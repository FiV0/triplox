# Mentat Transaction Processing Pipeline

A comprehensive overview of the algorithm a transaction goes through, from EDN input to committed datoms.

---

## Overview: The Type-Driven Pipeline

Mentat's transaction processor is a **multi-stage pipeline** where each stage is encoded in the Rust type system. The key insight is that the `Term<E, V>` generic type narrows its type parameters at each stage, making it impossible to accidentally pass unresolved tempids to a stage that expects concrete entids:

```rust
enum Term<E, V> {
    AddOrRetract(OpType, E, Entid, V)
    //                   ^    ^    ^
    //          entity slot  attr  value slot
}
```

Note: the attribute position (`a`) is **always** a concrete `Entid` — it's resolved in Stage 1 and never deferred.

The pipeline stages, with their concrete Term instantiations:

```
Stage 1 output:  TermWithTempIdsAndLookupRefs
                 = Term<Either<KnownEntid, LookupRefOrTempId>,
                        Either<TypedValue,  LookupRefOrTempId>>

Stage 2 output:  TermWithTempIds
                 = Term<Either<KnownEntid, TempIdHandle>,
                        Either<TypedValue,  TempIdHandle>>

Stage 3 output:  TermWithoutTempIds
                 = Term<KnownEntid, TypedValue>
```

Each stage eliminates one class of unresolved reference. The `Either` type (`Left` = resolved, `Right` = still pending) carries this status at the type level.

## Input Data Structures

### Entity (from EDN)

Defined in `edn/src/entities.rs`. Two forms:

```rust
enum Entity<V> {
    AddOrRetract { op: OpType, e: EntityPlace<V>, a: EntidOrIdent, v: ValuePlace<V> },
    MapNotation(BTreeMap<EntidOrIdent, ValuePlace<V>>),
}
```

### EntityPlace — what can appear in the entity position

```rust
enum EntityPlace<V> {
    Entid(EntidOrIdent),             // Literal entid or keyword ident
    TempId(ValueRc<TempId>),         // "my-temp-id"
    LookupRef(LookupRef<V>),         // (lookup-ref :attr value)
    TxFunction(TxFunction),          // (transaction-tx)
}
```

### ValuePlace — what can appear in the value position

```rust
enum ValuePlace<V> {
    Entid(EntidOrIdent),
    TempId(ValueRc<TempId>),
    LookupRef(LookupRef<V>),
    TxFunction(TxFunction),
    Atom(V),                          // A literal value (string, int, etc.)
    Vector(Vec<ValuePlace<V>>),       // Multiple values for cardinality-many
    MapNotation(MapNotation<V>),      // Nested entity map
}
```

### TempId — external (user-provided) vs internal (auto-generated)

```rust
enum TempId {
    External(String),    // From user: "my-temp-id" or :db/id "tempid"
    Internal(i64),       // Generated by Mentat for implicit entities (e.g. maps without :db/id)
}
```

### Core Schema Types (`core-traits/lib.rs`)

```rust
struct Attribute {
    value_type: ValueType,         // Ref, Long, String, Keyword, Boolean, Double, Instant, Uuid
    multival: bool,                // cardinality one (false) vs many (true)
    unique: Option<Unique>,        // None, Some(Value), Some(Identity)
    index: bool,                   // AVET indexed?
    fulltext: bool,                // fulltext indexed?
    component: bool,               // is-component?
    no_history: bool,              // suppress history? (flag exists, not implemented)
}

enum Unique { Value, Identity }
```

### TransactableValue trait (`db/src/types.rs`, `db/src/internal_types.rs`)

Both EDN values (`ValueAndSpan`) and programmatic values (`TypedValue`) implement this trait, which defines how raw values enter the pipeline:

```rust
trait TransactableValue {
    fn into_typed_value(self, schema: &Schema, value_type: ValueType) -> Result<TypedValue>;
    fn into_entity_place(self) -> Result<EntityPlace<Self>>;
    fn as_tempid(&self) -> Option<TempId>;
}
```

For `ValueAndSpan` (EDN input), `into_entity_place` maps:
- Integer → `EntityPlace::Entid(EntidOrIdent::Entid(v))`
- Namespaced keyword → `EntityPlace::Entid(EntidOrIdent::Ident(v))`
- String → `EntityPlace::TempId(TempId::External(v))`
- List `(transaction-tx)` → `EntityPlace::TxFunction`
- List `(lookup-ref a v)` → `EntityPlace::LookupRef`

For `TypedValue` (programmatic input), `into_typed_value` is a simple type assertion rather than coercion.

## Stage 0: Map Notation Explosion

**Location:** `db/src/tx.rs` — beginning of `entities_into_terms_with_temp_ids_and_lookup_refs()`

Before the main pipeline begins, map notation is "exploded" into individual add/retract operations:

```
{:db/id "tempid"
 :person/name "Alice"
 :person/age 30}

    becomes

[:db/add "tempid" :person/name "Alice"]
[:db/add "tempid" :person/age 30]
```

Key behaviors:
- If `:db/id` is missing, an **internal tempid** is auto-generated
- **Nested maps** are recursively exploded, but only if the parent attribute has `:db/isComponent true` or the nested map contains a `:db/unique :db.unique/identity` attribute
- **Vectors** in value position (for cardinality-many) are exploded into separate assertions:
  `{:db/id "t" :person/aliases ["Al" "Ally"]}` becomes two separate `:db/add` operations
- **Reversed attributes** (`:person/_friends`) flip entity and value positions; only valid for `:db.type/ref` attributes

All exploded entities are pushed onto a **deque** (`VecDeque`) and processed iteratively, allowing nested structures to expand without recursion limits.

## Stage 1: Entity -> Term Conversion

**Location:** `db/src/tx.rs` — `entities_into_terms_with_temp_ids_and_lookup_refs()`

**Output type:** `Vec<TermWithTempIdsAndLookupRefs>`

This stage converts high-level `Entity` values into `Term` values, resolving what it can and preserving what it can't.

### Helper: InProcess

```rust
struct InProcess<'conn, 'a, W: TransactWatcher> {
    partition_map: &'a PartitionMap,
    schema: &'a Schema,
    watcher: &'a mut W,
    tempid_set: InternSet<TempId>,       // Arena for deduplicating tempids
    lookup_refs: InternSet<AVPair>,       // Arena for deduplicating lookup refs
}
```

`InternSet<T>` is a set-based arena that returns `ValueRc<T>` handles. Interning ensures **pointer equality** for identical tempids across the entire transaction, which is critical for the upsert resolution algorithm in Stage 3.

### Entity position resolution (`entity_e_into_term_e`)

| Input | Resolution | Output |
|-------|-----------|--------|
| `Entid(n)` (integer) | Validate via `partition_map.contains_entid(n)` | `Left(KnownEntid(n))` |
| `Ident(:keyword)` | Lookup in schema's ident map | `Left(KnownEntid(n))` |
| `TempId("t")` | Intern into shared tempid set | `Right(TempId(handle))` |
| `LookupRef(a, v)` | Validate `a` is `:db/unique`, intern | `Right(LookupRef(handle))` |
| `TxFunction(transaction-tx)` | Resolve to current tx entid | `Left(KnownEntid(tx))` |

### Attribute resolution

The attribute `a` in `[:db/add e a v]` is **always** resolved to a concrete `Entid` at this stage:
- Keyword idents like `:person/name` are looked up via `schema.require_attribute_for_entid()`
- Integer entids are validated as existing attributes
- This is why the `Term<E, V>` type has a bare `Entid` for the attribute — it's never deferred.

### Value position resolution (`entity_v_into_term_v`)

| Input | Attribute ValueType | Output |
|-------|-------------------|--------|
| `Atom(v)` | any | `Left(TypedValue)` — coerced via `schema.to_typed_value()` |
| `Entid(n)` | `:db.type/ref` | `Left(TypedValue::Ref(n))` |
| `Ident(:kw)` | `:db.type/ref` | `Left(TypedValue::Ref(resolved))` |
| `TempId("t")` | `:db.type/ref` | `Right(TempId(handle))` |
| String atom | `:db.type/ref` | `Right(TempId(handle))` — strings in ref position become tempids |
| `LookupRef(a, v)` | `:db.type/ref` | `Right(LookupRef(handle))` |
| `TxFunction` | `:db.type/ref` | `Left(TypedValue::Ref(tx))` |

Note: a string value for a `:db.type/ref` attribute is automatically interpreted as a tempid. This is how `[:db/add "alice" :person/friend "bob"]` works — `"bob"` becomes a tempid reference, not a string value.

### Validations at this stage

- `UnallocatedEntid(n)` — integer entid not in any partition's allocated range
- `UnrecognizedIdent(:kw)` — keyword not in schema
- `BadValuePair(v, type)` — value can't be coerced to attribute's value type
- Lookup ref attribute must have `:db/unique`
- Reversed attributes require the unreversed form to be `:db.type/ref`
- Nested map notation requires either `:db/isComponent` or unique identity attribute

### Data structure after Stage 1

```rust
// Captures both types of unresolved references:
enum LookupRefOrTempId {
    LookupRef(ValueRc<AVPair>),    // AVPair = (Entid, TypedValue) — an [a v] pair
    TempId(ValueRc<TempId>),
}

type TermWithTempIdsAndLookupRefs =
    Term<Either<KnownEntid, LookupRefOrTempId>,   // entity: resolved OR (lookup-ref | tempid)
         Either<TypedValue,  LookupRefOrTempId>>;  // value:  resolved OR (lookup-ref | tempid)
```

## Stage 2: Lookup Ref Resolution

**Location:** `db/src/tx.rs` — `resolve_lookup_refs()`

**Output type:** `Vec<TermWithTempIds>`

All `LookupRef` values are batch-resolved against the store via a single SQL query.

### SQL query (`resolve_avs` in `db/src/db.rs`)

```sql
SELECT a, v, value_type_tag, e
FROM datoms
WHERE index_avet IS NOT 0
  AND (a = ? AND value_type_tag = ? AND v = ?)
  OR  (a = ? AND value_type_tag = ? AND v = ?)
  ...
```

Chunked to stay within SQLite's variable count limits. Returns an `AVMap`:

```rust
type AVPair = (Entid, TypedValue);            // (attribute, value)
type AVMap = HashMap<AVPair, Entid>;           // (a, v) -> entity
```

### Resolution (`replace_lookup_ref` in `internal_types.rs`)

For each term, every `Right(LookupRefOrTempId::LookupRef(av))` is replaced with:
- `Left(KnownEntid(e))` or `Left(TypedValue::Ref(e))` if found in AVMap
- Error `UnrecognizedIdent` if not found

TempIds pass through unchanged: `Right(LookupRefOrTempId::TempId(t))` becomes `Right(TempIdHandle)`.

After this stage, the type system guarantees no lookup refs remain.

---

## Stage 3: Upsert Resolution & Tempid Allocation

**Location:** `db/src/upsert_resolution.rs`

This is the most complex stage. It resolves tempids either by **upserting** (finding an existing entity with matching `:db.unique/identity` values) or by **allocating** fresh entids from the partition map.

The algorithm is described as "evolutionary" — it runs in a loop where each iteration can resolve more tempids based on what was learned in the previous iteration.

### 3a: Initial Classification into Generations

The `Generation` struct classifies terms into populations:

```rust
struct Generation {
    upserts_e:   Vec<UpsertE>,            // Simple upserts
    upserts_ev:  Vec<UpsertEV>,           // Complex upserts (value is also a tempid)
    allocations: Vec<TermWithTempIds>,     // Everything else still referencing tempids
    upserted:    Vec<TermWithoutTempIds>,  // Confirmed to exist in store
    resolved:    Vec<TermWithoutTempIds>,  // Resolved via other upserts (may/may not be in store)
}

// Simple upsert: [:db/add TEMPID unique_attr concrete_value]
struct UpsertE(TempIdHandle, Entid, TypedValue);

// Complex upsert: [:db/add TEMPID unique_attr OTHER_TEMPID]
struct UpsertEV(TempIdHandle, Entid, TempIdHandle);
```

Classification rules (`Generation::from()`):

| Term shape | `a` is `:db.unique/identity`? | Destination |
|---|---|---|
| `[:db/add TEMPID a concrete_v]` | Yes | `upserts_e` (simple upsert) |
| `[:db/add TEMPID a TEMPID2]` | Yes | `upserts_ev` (complex upsert) |
| `[:db/add TEMPID a concrete_v]` | No | `allocations` |
| `[:db/add TEMPID a TEMPID2]` | No | `allocations` |
| `[:db/add known_e a TEMPID]` | any | `allocations` |
| `[:db/add known_e a known_v]` | any | **inert** (returned separately, skips evolution entirely) |

### 3b: The Evolution Loop

```
while generation.can_evolve():          // i.e., upserts_e is non-empty

    1. Collect [a, v] pairs from simple upserts
       temp_id_avs = [(tempid, (a, v)), ...]

    2. Query store via resolve_avs():
       SQL: SELECT a, v, value_type_tag, e FROM datoms WHERE ...
       Returns: TempIdMap { tempid -> KnownEntid } for those that matched

    3. Evolve the generation one step:
       generation = generation.evolve_one_step(&temp_id_map)
```

### 3c: Evolution Rules (`evolve_one_step`)

**Simple upserts (`upserts_e`):**

| tempid in map? | Action |
|---|---|
| Yes, maps to `KnownEntid(n)` | Move to `upserted` as `Term(Add, n, a, v)` |
| No (not in store) | Demote to `allocations` (will get a fresh entid later) |

**Complex upserts (`upserts_ev`):**

| t1 resolved? | t2 resolved? | Action |
|---|---|---|
| Either | Yes, t2 -> `n2` | **Promote** to simple upsert: `UpsertE(t1, a, Ref(n2))` — gets another chance to upsert on the next iteration |
| Yes, t1 -> `n1` | No | Demote to `allocations` with e=n1, v still tempid |
| No | No | Keep as `upserts_ev` for next iteration |

This is why it's called "evolution" — complex upserts can become simple upserts as their dependencies resolve, and those simple upserts can resolve on the next iteration. The loop continues until no more simple upserts remain (`can_evolve()` returns false when `upserts_e` is empty).

**Allocations** are also scanned each iteration — any allocation whose tempid(s) were resolved in this step has its tempids substituted. If both entity and value positions are resolved, the term moves to `resolved`.

### 3d: Post-Evolution — Union-Find & Allocation

After the evolution loop terminates (no more upserts can resolve), any remaining tempids need fresh entids allocated. But first, the algorithm must identify tempids that **must share the same entid**.

**Union-Find grouping** (using `petgraph::UnionFind`):

If multiple tempids appear as the entity of `:db.unique/identity` assertions with the same `[a, v]` pair, they must receive the **same** entid. The algorithm:

1. Collect all tempids still in `allocations`
2. Build a map: `(a, v_or_tempid)` -> `Vec<TempIdHandle>` for unique-identity assertions
3. Union-find groups tempids that must be identical
4. Assign **dense labels** (0, 1, 2, ...) to each equivalence class — deterministically sorted so `"a"` allocates before `"b"`

**Entid allocation** from the partition map:

```rust
// In db/src/types.rs
struct Partition {
    start: Entid,                   // First entid in range
    end: Entid,                     // One past last entid in range
    next_entid_to_allocate: Entid,  // Monotonically increasing counter
    allow_excision: bool,
}

type PartitionMap = BTreeMap<String, Partition>;
```

The `:db.part/user` partition allocates a contiguous block: `allocate_entids(n)` bumps `next_entid_to_allocate` by n and returns the range. Each dense label gets one entid from this range.

### 3e: Final Population Assembly (`into_final_populations`)

```rust
struct FinalPopulations {
    upserted:  Vec<TermWithoutTempIds>,  // Matched existing entities in the store
    resolved:  Vec<TermWithoutTempIds>,  // Resolved transitively via other upserts
    allocated: Vec<TermWithoutTempIds>,  // Got freshly allocated entids
}
```

All tempids are replaced with concrete `KnownEntid` values. `:db/retract` with unresolved tempids is an error — you can't retract something that doesn't exist.

The `TempIdMap` (HashMap<TempIdHandle, KnownEntid>) is preserved for the final `TxReport` so callers can discover what entids their tempids resolved to.

## Stage 4: Validation via AEV Trie

**Location:** `db/src/tx_checking.rs` + `db/src/tx.rs`

All resolved terms (upserted + resolved + allocated + inert) are assembled into an **AEV Trie** — a prefix-compressed data structure for efficient constraint checking:

```rust
// internal_types.rs
type AEVTrie<'schema> = BTreeMap<
    (Entid, &'schema Attribute),           // (a, attribute) — attribute level
    BTreeMap<
        Entid,                              // e — entity level
        AddAndRetract                       // collected operations
    >
>;

struct AddAndRetract {
    add:     BTreeSet<TypedValue>,          // Values being asserted
    retract: BTreeSet<TypedValue>,          // Values being retracted
}
```

### Type checking (`type_disagreements`)

For every `(e, a, v)` in both adds and retracts:
- Verify `v.value_type() == attribute.value_type`
- Collects **all** disagreements, not just the first (maximally helpful error reporting)

Returns: `TypeDisagreements = BTreeMap<(Entid, Entid, TypedValue), ValueType>`

### Cardinality checking (`cardinality_conflicts`)

For each `(e, a)` group:
- **`CardinalityOneAddConflict`**: `!attribute.multival && ars.add.len() > 1` — can't add two different values to a cardinality-one attribute in one transaction
- **`AddRetractConflict`**: `ars.retract.intersection(&ars.add)` is non-empty — can't both add and retract the same exact value in one transaction

### Transaction instant insertion

If no `:db/txInstant` was explicitly provided in the transaction, one is auto-inserted:
```
[:db/add <current-tx-entid> :db/txInstant <now>]
```

### Metadata tracking

The system tracks whether any "metadata" attributes were touched — these are the attributes that define the schema itself:
- `:db/ident`, `:db/valueType`, `:db/cardinality`, `:db/unique`
- `:db/index`, `:db/fulltext`, `:db/isComponent`, `:db/noHistory`

If any were modified, a schema rebuild is triggered after commit (Stage 7).

## Stage 5: SQL Search & Materialization

**Location:** `db/src/db.rs`

This stage determines which datoms are truly new, which replace existing values, and which are no-ops (already exist identically in the store).

### 5a: Classification by attribute properties

Terms are split into four groups based on the attribute:

| Group | Fulltext? | Cardinality | Search Table |
|-------|-----------|-------------|-------------|
| `non_fts_one` | No | One | `temp.inexact_searches` |
| `non_fts_many` | No | Many | `temp.exact_searches` |
| `fts_one` | Yes | One | `temp.inexact_searches` |
| `fts_many` | Yes | Many | `temp.exact_searches` |

The distinction matters because:
- **Exact search** (cardinality-many): must match `[e, a, v]` exactly to detect duplicates
- **Inexact search** (cardinality-one): matches `[e, a]` only — any existing value for this entity+attribute will be replaced

### 5b: Insertion into temporary search tables

Each term becomes a row:
```sql
(e0, a0, v0, value_type_tag0, added0, flags0)
```

Where `flags0` is a bitfield encoding the attribute's index properties:
- Bit 0: `IndexAVET`
- Bit 1: `IndexVAET`
- Bit 2: `IndexFulltext`
- Bit 3: `UniqueValue`

### 5c: The Search Query

```sql
INSERT INTO temp.search_results
SELECT t.e0, t.a0, t.v0, t.value_type_tag0, t.added0, t.flags0,
       ':db.cardinality/many', d.rowid, d.v
FROM temp.exact_searches AS t
LEFT JOIN datoms AS d
  ON t.e0 = d.e AND t.a0 = d.a
  AND t.value_type_tag0 = d.value_type_tag AND t.v0 = d.v

UNION ALL

SELECT t.e0, t.a0, t.v0, t.value_type_tag0, t.added0, t.flags0,
       ':db.cardinality/one', d.rowid, d.v
FROM temp.inexact_searches AS t
LEFT JOIN datoms AS d
  ON t.e0 = d.e AND t.a0 = d.a
```

The `LEFT JOIN` finds existing datom rowids and old values. The `search_results` table now contains everything needed to perform the actual update — including whether each assertion is genuinely new, a replacement, a duplicate, or a retraction.

### 5d: Datoms table update (`update_datoms`)

**Deletes** (explicit retractions + implicit cardinality-one replacements):
```sql
DELETE FROM datoms WHERE rowid IN (
    SELECT rid FROM temp.search_results
    WHERE rid IS NOT NULL
    AND ((added0 IS 0)                                                    -- explicit retraction
      OR (added0 IS 1 AND search_type IS ':db.cardinality/one'
          AND v0 IS NOT v))                                               -- implicit replacement
)
```

**Inserts** (new assertions + replacements):
```sql
INSERT INTO datoms (e, a, v, tx, value_type_tag,
                    index_avet, index_vaet, index_fulltext, unique_value)
SELECT e0, a0, v0, ?, value_type_tag0,
       (flags0 & 1) IS NOT 0,    -- IndexAVET
       (flags0 & 2) IS NOT 0,    -- IndexVAET
       (flags0 & 4) IS NOT 0,    -- IndexFulltext
       (flags0 & 8) IS NOT 0     -- UniqueValue
FROM temp.search_results
WHERE added0 IS 1
AND ((rid IS NULL)                                                        -- genuinely new
  OR (rid IS NOT NULL AND v0 IS NOT v))                                   -- replacing old value
```

Key insight: if `rid IS NOT NULL AND v0 IS v`, that's a **no-op** — the datom already exists identically. It's neither deleted nor re-inserted.

## Stage 6: Transaction Log Commit

**Location:** `db/src/db.rs` — `insert_transaction()`

Every effective change (not no-ops) is recorded in the `timelined_transactions` table.

**Additions:**
```sql
INSERT INTO timelined_transactions (e, a, v, tx, added, value_type_tag)
SELECT e0, a0, v0, ?, 1, value_type_tag0
FROM temp.search_results
WHERE added0 IS 1 AND ((rid IS NULL) OR (rid IS NOT NULL AND v0 IS NOT v))
```

**Retractions** (including implicit ones from cardinality-one replacement):
```sql
INSERT INTO timelined_transactions (e, a, v, tx, added, value_type_tag)
SELECT DISTINCT e0, a0, v, ?, 0, value_type_tag0
FROM temp.search_results
WHERE rid IS NOT NULL
AND ((added0 IS 0)
  OR (added0 IS 1 AND search_type IS ':db.cardinality/one' AND v0 IS NOT v))
```

Note: for cardinality-one replacement, the **old** value `v` (from the existing datom, not `v0`) is recorded as the retracted value. This preserves the full history of what was removed.

---

## Stage 7: Schema & Metadata Update (conditional)

**Location:** `db/src/tx.rs` + `db/src/db.rs`

Only runs if `tx_might_update_metadata` was flagged in Stage 4.

1. **Extract metadata assertions** from `temp.search_results` — filter for known schema attribute entids
2. **Rebuild** `Schema` (ident map + attribute map) from the new datoms via `update_schema_from_entid_quadruples()`
3. **Validate** schema constraints (`db/src/schema.rs`, `AttributeValidation` trait):
   - `:db/unique` requires `:db/index true`
   - `:db/fulltext` requires `:db/valueType :db.type/string` and `:db/index true`
   - `:db/isComponent` requires `:db/valueType :db.type/ref`
4. **Update materialized views**: `idents` and `schema` tables are repopulated
5. **Update datom index flags** for any attributes whose indexing properties changed

---

## Stage 8: Output

**Location:** `db/src/tx.rs`

The transaction returns a `TxReport`:

```rust
struct TxReport {
    tx_id: Entid,                              // The transaction's own entid
    tx_instant: DateTime<Utc>,                 // When the transaction was committed
    tempids: BTreeMap<String, KnownEntid>,     // User-facing map: tempid string -> allocated entid
}
```

The `tempids` map only contains **external** tempids (user-provided strings), not internal ones (auto-generated for maps without `:db/id`). This is the caller's way to discover what entids were assigned.

## Complete Flow Diagram

```
                        EDN string or Vec<Entity<TypedValue>>
                                       |
                          +------------+------------+
                          |                         |
                    MapNotation               AddOrRetract
                          |                         |
                    [Stage 0: Explosion]            |
                    - auto-generate :db/id          |
                    - expand nested maps            |
                    - expand vectors                |
                          |                         |
                          +--------> VecDeque <-----+
                                       |
                          [Stage 1: Entity -> Term]
                          - resolve known entids via PartitionMap
                          - resolve idents via Schema
                          - resolve attributes to Entid
                          - coerce values via schema.to_typed_value()
                          - intern tempids & lookup refs
                                       |
                                       v
                       Vec<TermWithTempIdsAndLookupRefs>
                       Term<Either<KnownEntid, LookupRefOrTempId>,
                            Either<TypedValue,  LookupRefOrTempId>>
                                       |
                          [Stage 2: Lookup Ref Resolution]
                          - batch SQL: resolve_avs()
                          - replace LookupRef -> KnownEntid
                                       |
                                       v
                            Vec<TermWithTempIds>
                            Term<Either<KnownEntid, TempIdHandle>,
                                 Either<TypedValue,  TempIdHandle>>
                                       |
                    +------------------+------------------+
                    |                                     |
               inert terms                          Generation
               (no tempids)                    +----+----+----+----+
                    |                          | upserts_e         |
                    |                          | upserts_ev        |
                    |                          | allocations       |
                    |                          +-------------------+
                    |                                     |
                    |                [Stage 3a: Evolution Loop]
                    |                while can_evolve():
                    |                  - collect [a,v] from upserts_e
                    |                  - SQL: resolve_avs()
                    |                  - evolve_one_step()
                    |                  - promote/demote/resolve
                    |                                     |
                    |                [Stage 3b: Union-Find]
                    |                - group equivalent tempids
                    |                - dense labeling
                    |                                     |
                    |                [Stage 3c: Allocation]
                    |                - partition_map.allocate_entids(n)
                    |                - build TempIdMap
                    |                                     |
                    |                          FinalPopulations
                    |                    { upserted, resolved, allocated }
                    |                                     |
                    +------------> all TermWithoutTempIds <+
                                  Term<KnownEntid, TypedValue>
                                           |
                              [Stage 4: Validation]
                              - build AEV Trie
                              - type_disagreements()
                              - cardinality_conflicts()
                              - insert :db/txInstant if missing
                                           |
                              [Stage 5: SQL Materialization]
                              - classify by fulltext x cardinality
                              - insert into temp search tables
                              - LEFT JOIN against datoms
                              - delete old + insert new
                                           |
                              [Stage 6: Transaction Log]
                              - insert into timelined_transactions
                              - record adds (added=1) and retracts (added=0)
                                           |
                              [Stage 7: Schema Update] (if metadata changed)
                              - rebuild Schema from datoms
                              - validate constraints
                              - update materialized views
                                           |
                                           v
                                       TxReport
                                { tx_id, tx_instant, tempids }
```

## End-to-End Example

Given this transaction:
```edn
[{:db/id "alice"
  :person/name "Alice"
  :person/email "alice@example.com"}    ;; :person/email is :db.unique/identity
 [:db/add "bob" :person/friend "alice"]]
```

**Stage 0 — Explosion:**
```
[:db/add "alice" :person/name "Alice"]
[:db/add "alice" :person/email "alice@example.com"]
[:db/add "bob" :person/friend "alice"]
```

**Stage 1 — Entity->Term** (assuming :person/name=123, :person/email=124, :person/friend=125):
```
Term(Add, Right(TempId("alice")), 123, Left(String("Alice")))
Term(Add, Right(TempId("alice")), 124, Left(String("alice@example.com")))
Term(Add, Right(TempId("bob")),   125, Right(TempId("alice")))
```
Note: `"alice"` in value position of `:person/friend` (a `:db.type/ref` attr) becomes a TempId, not a string.

**Stage 2 — LookupRef resolution:** No lookup refs, pass-through.

**Stage 3 — Upsert resolution:**
- Classification:
  - `[:db/add "alice" :person/email "alice@example.com"]` -> `upserts_e` (unique identity attr)
  - `[:db/add "alice" :person/name "Alice"]` -> `allocations` (not unique)
  - `[:db/add "bob" :person/friend "alice"]` -> `allocations` (not unique, value is tempid)
- Evolution iteration 1:
  - Query store for `(:person/email, "alice@example.com")`
  - **Found entity 42** -> `TempIdMap {"alice" -> KnownEntid(42)}`
  - Simple upsert for "alice" -> `upserted`
  - Allocation for "alice"'s name: tempid resolved -> `resolved` as `Term(Add, 42, 123, "Alice")`
  - Allocation for "bob"'s friend: "alice" resolved to 42 -> `allocations` still has "bob"
- Evolution iteration 2: `upserts_e` is empty -> loop terminates
- Union-find: "bob" is alone, gets dense label 0
- Allocate 1 entid from `:db.part/user` -> "bob" = 1001

**Stage 4 — Validation:**
- Type check: all values match their attribute types
- Cardinality: no conflicts
- Auto-insert `:db/txInstant`

**Stages 5-6 — SQL materialization & commit:**
- `:person/name` for entity 42: inexact search finds existing row -> DELETE old + INSERT new (if different)
- `:person/email` for entity 42: exact search finds identical row -> NO-OP (already exists)
- `:person/friend` for entity 1001: no existing row -> INSERT

**Stage 8 — Output:**
```rust
TxReport {
    tx_id: 268435457,
    tx_instant: 2024-01-01T00:00:00Z,
    tempids: {"alice" -> 42, "bob" -> 1001},
}
```
