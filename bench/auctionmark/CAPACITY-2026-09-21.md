# AuctionMark incremental-query stress runs, 2026-09-21

At 1,000 distinct live queries and five writes/second, Triplox accepted writes
promptly but accumulated tens of seconds of delivery lag. A 10,000-query attempt
with 2,000 users and 10,000 items exhausted the memory limit during registration,
long before all subscriptions were open. Reducing the fixture to 2,000 items still
exhausted memory at roughly 1,772 subscription circuit attempts.

These are bounded local experiments on this branch, not a universal subscription
limit. Each configuration was run once. No engine or client implementation was
changed, and no commits were created.

## Configuration

- Checkout: `3c6500326c048bac7de36d542e089a04d90adf82`.
- Intel Core Ultra 7 258V, Linux `6.18.44-1-MANJARO`.
- OpenJDK **26.0.2**, OkHttp 4.12.0, virtual readers and consumers.
- Existing release executable: `target/auctionmark-validation/triplox`.
  SHA-256: `be0f39d5b49811d16e29f65133bfbba6599163f5f17d2291f084fefeb868d14e`.
  Its hash matches the earlier recorded release build. The server, client,
  benchmark, Cargo manifest and lockfile have no changes since `9f8c0d67e`.
- Pooled DBSP: two foreground workers, one merger, 4,096 MiB cache capacity.
  Feldera revision: `ded0d390b64bdfe82a9afac9084404ad3809547e`.
- Server/client scope: 1.75 CPU cores, 7,424 MiB memory, no swap, 1,024 tasks.
  MinIO: 0.25 cores, 768 MiB. Combined budget: **two cores and 8 GiB**.
- Fresh disposable database for every run; seed 42; target five committed
  transactions/second; 10 seconds warmup and 30 seconds measurement.
- All five `auctionmark.live` families: item, watchlist, selling, bids, questions.
  Queries have embedded user/item constants and are distinct within each run.
- CDC polling remains 200 ms; configured remote WAL flush remains 100 microseconds.

Java 26 removes the observed Java 21 registration obstacle in these tests:
1,000 subscriptions primed with 38–39 client OS threads, without increasing the
virtual-thread scheduler's carrier limit.

## Results

| Run | Users / items | Completed initializations | Outcome |
|---|---|---:|---|
| 1,000 queries, normal 5 s backlog guard | 200 / 1,000 | 1,000 in 33.96 s | Aborted during warmup; 57 deliveries pending |
| 1,000 queries, diagnostic 60 s backlog/drain allowance | 200 / 1,000 | 1,000 in 33.44 s | All results verified; p95 delivery latency 52.88 s |
| 10,000-query target | 2,000 / 10,000 | Incomplete; about 577 subscription circuits attempted | Triplox killed by the memory cgroup after 206.7 s |
| 10,000-query target, minimum fixture | 2,000 / 2,000 | At least 1,700 primed; about 1,772 circuits attempted | Triplox killed by the memory cgroup after 224.1 s |

The normal 1,000-query run failed with `Expected delivery exceeded backlog age
limit`. Server peak RSS was 1,992 MiB; combined peak RSS was 2,641 MiB. It never
entered the measurement window, so the report's zero measured transactions and
null percentiles are not throughput or latency measurements. Pending deliveries
at this early abort do not establish data loss.

The diagnostic retry changed only the backlog/drain allowance to 60 seconds and
added progress logging through a temporary wrapper. The 250 ms freshness target
remained unchanged. Its completed measurement was:

| Metric | Result |
|---|---:|
| Measured committed transactions | 149 in 30 s, **4.97 tx/s** |
| Total committed transactions including warmup | 199 |
| Measured expected / received deliveries | 329 / 329 |
| Submission-to-applied latency p50 / p95 / p99 / maximum | 34.32 / **52.88** / 54.02 / 54.18 s |
| Transaction acknowledgement p95 | 12.95 ms |
| Write scheduling delay p95 | 1.06 ms |
| Changed subscriptions per measured transaction, median / p95 / maximum | 2 / 6 / 7 |
| Unchanged measured query/transaction pairs | 148,671 of 149,000 |
| Pending deliveries when writes stopped | 259 |
| Final missing / unmatched deliveries / correctness errors | 0 / 0 / 0 |
| Final result rows per query, median / p95 / maximum | 1 / 5 / 8 |

| Combined sampled peak RSS, including MinIO | 6,512 MiB |
| Server / client peak OS threads before cleanup | 14 / 39 |

Latency includes arrivals during the final drain for transactions submitted in
the measurement window. Every final subscription bag matched both the reference
model and an ordinary database query. The sole failed check was freshness.
This shows finite catch-up for this bounded write burst, not sustainable service
at five writes/second indefinitely.

The larger fixture ran out of memory **before workload writes started**. Kernel
logs identify `triplox`, PID 35830, as the killed process, with approximately
7,036 MiB resident memory. The cgroup recorded `oom 1` and `oom_kill 1`, and reached
its 7,424 MiB limit. Systemd then terminated the remaining application processes;
the launcher's `Received signal 15` is a consequence of that OOM. There is no
completed driver report or valid latency/throughput sample for this attempt.

Its log contains 578 circuit-construction messages, including one startup circuit.
Thus approximately 577 subscription circuits were attempted; this is not an exact
count of successfully primed clients. Sampled server RSS grew with registration:

| Subscription circuit attempts, approximately | Server RSS (MiB) |
|---:|---:|
| 105 | 1,711 |
| 206 | 2,848 |
| 300 | 3,914 |
| 404 | 5,095 |
| 501 | 6,203 |

That interval grew by roughly 11 MiB per additional subscription, averaged across
the five families. Counts and RSS were sampled every two seconds. This is a
measured local slope, not an extrapolated capacity claim.

The last run reduced the item count to 2,000, the minimum permitted by the driver
for 10,000 distinct queries: five queries per user and at least one item per user.
Progress logging confirmed 1,700 completed primings at 211.5 seconds after the
probe loaded. There were 1,773 total circuit-construction messages, including the
startup circuit, when the memory cgroup killed Triplox, PID 42877. The kernel
reported approximately 7,043 MiB resident memory; the cgroup again recorded one
OOM kill at its 7,424 MiB limit. Total scope duration was 224.1 seconds. This run
also never reached workload writes and produced no completed driver report.

The two registration failures show why query count alone is insufficient:
fixture size changes the failure point substantially. Neither attempted target
is a measurement of 10,000 simultaneously active queries. The confirmed 1,700
primings in the smaller-fixture run are not a tested write-serving capacity.

An external sample also caught **523 server OS threads during teardown** of the
successful-drain run. The driver's own sampler stops before subscription cleanup,
so its 14-thread maximum excludes that phase. The worker cleanup path independently
spawns blocking circuit-destruction jobs; the observation warrants a separate
cleanup investigation and is not the cause of the measured delivery latency.

## What the implementation explains

Small final results do not imply small retained join inputs:

1. [`scan_current_triples`](../../src/incremental/cdc.rs) scans the entire EAV
   range separately for registration, retaining triples for all attributes used
   by that query. It does not restrict this scan by the query's user/item constant.
2. [`pattern_stream` and `join_pattern_streams`](../../src/incremental/circuit.rs)
   build each pattern stream from that input and independently index both sides
   of each join. Constants filter their own pattern; the selected user's entities
   do not restrict all subsequent pattern inputs before those inputs are indexed.
   Each subscription builds its own circuit.
3. [`apply_triples`](../../src/incremental.rs) sends every later transaction batch
   to every registered query, without attribute or parameter routing. The
   [worker](../../src/incremental/worker.rs) clones its triples and steps its circuit
   even when that transaction produces no result change.

These paths support investigating duplicated join-input state and per-query work
on irrelevant transactions. The experiment did not collect a heap or CPU profile,
so it does not assign an exact percentage of memory or latency to either mechanism.
The evidence is not a measured combinatorial explosion of final join results.

## Reproduction and artifacts

Run from the worktree root with the verified release binary. Each output directory
must be new. Java is selected only for these processes; the system default is not
changed.

```bash
export JAVA_HOME=/usr/lib/jvm/java-26-openjdk
export PATH="$JAVA_HOME/bin:$PATH"

python3 bench/auctionmark/run-sync.py \
  --server-binary target/auctionmark-validation/triplox \
  --output-dir target/auctionmark-sync/reproduce-1000 --timeout 600 -- \
  --mode capacity --stages 1000 --users 200 --items 1000 \
  --rate 5 --warmup 10 --duration 30

# Separate fresh run: allow delayed updates to drain and verify final results.
python3 bench/auctionmark/run-sync.py \
  --server-binary target/auctionmark-validation/triplox \
  --output-dir target/auctionmark-sync/reproduce-1000-drain --timeout 600 -- \
  --mode capacity --stages 1000 --users 200 --items 1000 \
  --rate 5 --warmup 10 --duration 30 --drain-ms 60000

python3 bench/auctionmark/run-sync.py \
  --server-binary target/auctionmark-validation/triplox \
  --output-dir target/auctionmark-sync/reproduce-10000 --timeout 900 -- \
  --mode capacity --stages 10000 --users 2000 --items 10000 \
  --rate 5 --warmup 10 --duration 30

# Minimum fixture for 10,000 distinct queries.
python3 bench/auctionmark/run-sync.py \
  --server-binary target/auctionmark-validation/triplox \
  --output-dir target/auctionmark-sync/reproduce-10000-small --timeout 900 -- \
  --mode capacity --stages 10000 --users 2000 --items 2000 \
  --rate 5 --warmup 10 --duration 30
```

Local artifacts are under
[`target/auctionmark-sync/stress-20260921/`](../../target/auctionmark-sync/stress-20260921/):

- `1000/report.json` and `1000-relaxed/report.json`: full driver measurements.
- `10000/` and `10000-small/`: configurations, server/MinIO logs and launcher metadata.
- `*-client.log`, `*-samples.jsonl`, `*-cgroup.jsonl`,
  `*-kernel.log`, and `*-systemd.log`: progress and process/cgroup evidence.
- `memory-by-circuit-count.csv`: external RSS samples alongside circuit counts.
- `provenance.json`, `client-classpath.txt`: environment and executable identity.
- `probe.clj`, `run-probe.py`, `monitor.py`: temporary progress logging and sampling.
  The wrapper adds logging around the existing driver functions. The commands
  above reproduce the workload and limits without that extra logging.

The 1,000-query diagnostic report's `dirty: true` came from Python creating an untracked
`bench/auctionmark/__pycache__` while importing the launcher. That generated file
was removed, and subsequent imports disabled bytecode writes. Application source
was unchanged throughout these baseline experiments. The minimum-fixture run was
marked dirty because this report was being written. At baseline completion, this
report was the only addition outside the ignored experiment artifacts. All
benchmark processes and disposable MinIO containers were cleaned up after those runs.

## Follow-up: 6 GiB DBSP process RSS budget

Added `.with_max_rss_bytes(Some(6_u64 * 1024 * 1024 * 1024))` to the shared pool
construction in `src/incremental.rs`. This sets DBSP's process-wide pressure
budget to 6,442,450,944 bytes. It is a soft pressure threshold; the existing
7,424 MiB application cgroup remains the hard limit. The cache remains 4,096 MiB.
No other production code or workload setting changed.

The rebuilt release executable is `target/release/triplox`, SHA-256
`e5911ec25a46c54ca041610444235f1c113d0c7c9fafa5b8bbf9ebccf21ff880`.
The checkout revision remains `3c6500326`; the source change is uncommitted and
recorded in the new provenance file. Java 26, the fixtures, seed, CPU/memory
quotas, and 600/900-second client timeouts match the baseline. Runs used separate
fresh databases and the same temporary progress wrapper.

| Run | Without RSS budget | With 6 GiB RSS budget |
|---|---|---|
| 1,000 queries, 5 s backlog guard | All primed; warmup aborted with 57 deliveries pending | All primed in 34.88 s; warmup aborted with 55 deliveries pending |
| 1,000 queries, 60 s drain | All results verified; p95 52.88 s | Drain expired with pending deliveries; final report retained 54 pending |
| 10,000 target, 2,000 users / 10,000 items | OOM near 577 circuit attempts, 206.7 s | OOM near 489 attempts, 186.0 s |
| 10,000 target, 2,000 users / 2,000 items | OOM near 1,772 circuit attempts, 224.1 s | OOM near 1,499 attempts, 211.5 s |

OOM timings are systemd scope wall times. Circuit counts exclude the one startup
circuit and are attempts, not exact successful-priming counts. Progress logs
confirmed at least 400 and 1,400 completed initializations in the two new OOM runs.
Neither reached workload writes. Each configuration is one trial, so these are
observations rather than a statistically established change in capacity.

The 60-second-drain run accepted 150 measured transactions at 5.0 tx/s and expected
330 measured deliveries. It observed only 277 measured deliveries before teardown;
54 pending deliveries in the report include both warmup and measured transactions.
The reported 49.75 s p95 is therefore incomplete and must not be interpreted as a
latency improvement over the fully drained baseline. There were 52 final-client
mismatches while updates remained pending, zero unexpected deliveries and no
final-database mismatches. This does not by itself establish data loss or incorrect
individual deltas. Server sampled peak RSS was 5,708 MiB and combined peak RSS was
6,470 MiB.

The setting did activate spilling during registration, but did not prevent OOM:

- On the larger fixture, files first appeared in the external samples near
  5,320 MiB server RSS. Once RSS crossed roughly 5,530 MiB, it climbed from
  5,522 to 6,743 MiB in eight seconds. The sampled batch-file data reached
  284 MiB before the kernel killed Triplox.
- On the smaller fixture, spilling was also active before the failure. RSS rose
  from 5,536 to 6,949 MiB over sixteen seconds; sampled batch-file data reached
  219 MiB. The hard cgroup limit was reached again.
- Both kernel logs identify `merger-0` as the thread invoking the OOM killer and
  `triplox` as the killed process. At the kills, the cgroups contained about
  7.7 GB of anonymous memory and almost no file-cache memory. Unreclaimed file
  cache therefore does not explain these OOMs.

This establishes that the pressure setting is wired through and disk spilling
starts. It also shows that starting that work at this budget does not provide
enough effective headroom in this setup. The precise anonymous-memory allocation
growth during spilling has not been heap-profiled; these runs do not establish
which buffers, retained batches, cache allocations, or allocator behavior account
for it. No additional cache tuning or runtime changes were made.

A final fresh 1,000-query run increased only the backlog/drain allowance to
180 seconds to distinguish slow catch-up from missing results. It initialized all
queries in 35.26 seconds, accepted 150 measured transactions at 5.0 tx/s, and
eventually received all 330 expected measured deliveries. The final result bags
matched both the reference model and ordinary database queries; there were zero
missing, unmatched or incorrect results. Delivery latency p50/p95/p99/maximum was
32.57 / **131.90** / 146.25 / 149.56 seconds. The only failed check was freshness.
Server peak RSS was 5,675 MiB, combined peak RSS 6,491 MiB, and server file
descriptors peaked at 32,745. There was no OOM event in this run. This establishes
eventual catch-up for that bounded burst, with substantially worse observed tail
latency than the 52.88 s baseline, not sustainable five-tx/s service.

Its report and logs are named `1000-drain180`. Reproduce it with the 1,000-query
command, the new release binary, a fresh output directory and `--drain-ms 180000`.
The previous 60-second-drain mismatch observations were therefore consistent with
slow delivery; the longer run did not reproduce a final correctness failure.
